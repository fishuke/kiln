# #129: SQLite runtime store

## Why

`FileStore` holds all runtime state in memory and rewrites the whole `kiln.json` on every write. Real installs reach several MB, so each `put` serializes and rewrites everything, and two writers can lose each other's changes.

## Goal

Runtime state lives in SQLite at `<dataDir>/kiln.db`, behind the same synchronous `Store` interface. Nothing else in the engine changes.

## Approach

- `SqliteStore` (packages/store) uses Node's built-in `node:sqlite` (synchronous, no native build). One table `documents(collection, id, json)` with primary key `(collection, id)`, WAL journal, `synchronous=NORMAL`.
- `get`/`list` parse the stored JSON, so callers always get fresh copies. `list` filters in JS for now.
- `transaction(fn)` runs BEGIN … COMMIT, and ROLLBACK when `fn` throws. A nested call uses a savepoint, so an inner failure undoes only the inner writes, like `MemoryStore`.
- `openRuntimeStore(dataDir, env)` (apps/api/src/runtime-store.ts, used by config.ts) picks the store: `KILN_STORE=file` keeps `FileStore` on `kiln.json` for one release; otherwise `SqliteStore` on `kiln.db`. When `kiln.json` exists and `kiln.db` does not, it imports every document in one transaction and renames the file to `kiln.json.imported`.
- ADR-015 supersedes the storage part of ADR-005. Postgres stays a later step behind an async refactor.

## Acceptance criteria

- AC1: One store contract suite passes for `MemoryStore`, `FileStore` and `SqliteStore`.
- AC2: An existing `kiln.json` is imported once into `kiln.db` and renamed; a second start does not import again.
- AC3: `KILN_STORE=file` uses `kiln.json` as before.
- AC4: The self-hosting docs describe `kiln.db`, backups and `KILN_STORE`.
