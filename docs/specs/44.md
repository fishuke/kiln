# #44: Easy, generic MCP setup and testing

## Why
Adding an observability MCP (the trigger: SigNoz for poe-bot) meant knowing a hidden built-in name, creating raw secrets in a blank form with no idea what the values were, and editing the runner's egress by hand. Teams use many such servers (SigNoz, Datadog, New Relic, Better Stack, their own), so baking one vendor in is the wrong fix.

## Goal
Any MCP server is easy to add and easy to check, at team, factory and agent level, with one mechanism, not one per vendor or per scope.

## Approach
- **Templates carry fields.** A template (`apps/web/src/lib/mcp-config.ts`) lists the values a server needs: label, hint, URL or password, secret or not. One form (`McpFields`) renders any template. Secret fields become team secrets; other fields are written into the config. Built-in servers reuse the same form for their secrets. SigNoz moves from built in to a template (URL server: SigNoz Cloud or self-hosted HTTP mode); its binary leaves the runner image.
- **One test.** `McpRegistry.testServers(team, { factory?, agent?, servers? })` resolves servers the way a run does and probes URL servers through `McpProbe` (`HttpMcpProbe`: streamable HTTP `initialize` + `tools/list`; `FakeMcpProbe` in tests). One route (`POST /api/v1/mcp-servers/test`) and one button (`McpTestButton`) serve every scope.
- **Egress follows MCP.** A run's allowlist gets the hosts of its URL servers and URL-valued secrets.

## Acceptance
- Agent → Add MCP lists the team's servers, built-ins (with a connect form when not connected) and templates.
- Picking a template asks for its fields; saving stores the keys and registers the server.
- Test shows tools or a clear error for the team, a factory and an agent.
- A run using an MCP server can reach its host without editing egress.
