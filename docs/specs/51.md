# #51: SigNoz template: choose Cloud or Self-hosted

## Why
Self-hosted SigNoz has no MCP endpoint, and SigNoz Cloud's hosted MCP refuses self-hosted instances (HTTP 403). The template only offered a URL server, so self-hosted teams had to deploy `signoz-mcp-server` somewhere public first. Locally the same server just runs as stdio with `SIGNOZ_URL` and `SIGNOZ_API_KEY`.

## Goal
Picking SigNoz asks how it runs: SigNoz Cloud or Self-hosted. Self-hosted works with only a URL and a key.

## Approach
- **Templates can have variants** (`apps/web/src/lib/mcp-config.ts`): each has a label, a hint, a server shape, a mode and fields. The template's own server and fields are its first variant, so code that ignores variants still gets a working default. `pickVariant` resolves one; `VariantChoice` renders the choice in the MCP dialog and in Agent → Add MCP. Not SigNoz-specific: any template can list variants.
- **SigNoz Self-hosted** is a direct (stdio) server: `signoz-mcp-server` with `SIGNOZ_URL` written in and `SIGNOZ_API_KEY` as a team secret. The sandbox image ships the binary, pinned and checksum-verified, like the Playwright MCP server. This reverses #44's removal of the binary; #44 removed the *built-in server*, which stays removed.
- **Egress**: a command server's literal URL values (env and args) join the run's allowlist, next to URL servers and URL-valued secrets.

## Acceptance
- SigNoz shows SigNoz Cloud and Self-hosted; each shows its own fields.
- Self-hosted saves a command server with SIGNOZ_URL and a SIGNOZ_API_KEY secret.
- A run using it can reach the SigNoz URL without editing egress.

## Also fixed
Template keys went through `PUT /api/v1/secrets`, which for a server admin writes a server secret. Runs still found it (server secrets are the fallback), but the MCP page looked for a team secret and showed "Needs SIGNOZ_API_KEY" with no Test button. `createTeamSecret` now always writes the current team's managed secret.
