# #71: Agent foreman

## Why
The foreman is a fixed stage loop. It can't adjust the plan, tell the requester what is happening in its own words, or send work back to the agent that has the context. Tasks read as a list of runs.

## Goal
A factory can make its foreman an agent that plans, delegates, narrates and is woken by events, without giving up durability, gates or budgets.

## Approach
See ADR-011. `factory.yaml` `foreman: { mode: agent, maxTurns }` (packages/schema). `packages/engine/src/agent-foreman.ts` holds the action schema and the turn prompt. `Workflow` runs turns (`foremanTurn`), carries out actions (`applyActions`), starts agents in the background (`dispatch`) and records events (`queue`). People's messages, gate decisions, CI and restarts become events. Finished runs land on the work item at the start of the next turn (`absorbRun`): cost, triage, spec, review and the pull request.

## Acceptance criteria
- AC1: With `mode: agent`, a request goes triage → implement → review → hand-off with one foreman turn per event, a checklist and the foreman's own messages. Subagents don't write to the conversation.
- AC2: `ask` opens a question with options; no turn runs until a person answers; the answer wakes the foreman.
- AC3: A person's message after hand-off goes to the implement agent as a continuation of its run.
- AC4: After a restart, an agent-mode task gets a `restarted` event instead of stopping.
- AC5: The turn limit parks the task with a question that names the reason.
